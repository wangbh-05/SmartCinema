# SmartCinema 技术方案讲解文稿

本稿对应答辩 PPT 的“技术方案讲解”部分，顺序为：模块 3 影院热度地图、模块 2 跨端 Canvas 选座、模块 1 智能推荐选座、AI 偏好理解。PPT 保持简洁；讲解时可用本稿补充设计动机、算法边界与源码依据。

## 0. 总体讲法

建议用 4--5 分钟讲完这一节。每一页都采用“问题 -> 方案 -> 收益”的结构：

1. 先说明用户面对的实际困难；
2. 再用一张流程图解释代码怎样处理；
3. 最后马上在网页中演示对应结果。

系统坚持一个边界：**表现层负责交互和可视化，领域/应用层负责规则和状态。** 因此 Canvas、AI 或 LocalStorage 都不能绕过库存与选座规则。

## 1. 模块 3：影院热度地图

### 要讲什么

普通座位图只能显示“这个座位是否被占用”。SmartCinema 将每个座位的受欢迎程度扩展为连续热度场，让用户快速读出一片区域的趋势；同时保留座位层，仍能准确点击每一个座位。

### 实现一：弧形座位的几何布局

源码位置：[`src/ui/canvas/CanvasSeatMapView.js`](../src/ui/canvas/CanvasSeatMapView.js)

```js
const normalizedX = halfSpan === 0 ? 0 : (seatOffsetX - halfSpan) / halfSpan;
const curveOffset = curveDepth * (1 - normalizedX * normalizedX);
const x = startX + seatOffsetX;
const y = top + seat.rowIndex * rowStep + curveOffset;
const slope = halfSpan === 0 ? 0 : (-2 * curveDepth * normalizedX) / halfSpan;
```

- `normalizedX` 把每个座位的横向位置归一化到影厅中心两侧；
- `curveOffset = depth * (1 - x^2)` 是一条开口向下的抛物线：中间座位下沉、两侧上扬，形成面向银幕展开的视觉效果；
- `slope` 是抛物线在该位置的切线斜率，座椅再据此轻微旋转，因此不只是“把座位排成弧线”。

代码还会比较相邻列的 `sectionId`，在分区变化的地方加入额外间隔，避免把过道误画成普通座位间距。

### 实现二：从离散点到连续热力场

热图由第二张 Canvas 绘制。每个像素会累加附近座位的高斯权重：

```js
const weight = Math.exp(-distanceSquared / (2 * radiusSquared));
weightedHeat += sample.heat * weight;
totalWeight += weight;
const heat = clamp(weightedHeat / totalWeight);
```

- 距离座位越近，`weight` 越大；
- 多个相邻高热座位会自然叠加成热区，不会出现生硬的方格；
- 半径随影厅列数变化，避免小厅过度模糊或大厅过于零散；
- 最终按冷色、暖色、热色、强调色插值，并在边缘逐渐淡出。

星期切换也不是随机变化。代码以 `seat.id + period` 做稳定哈希，再叠加周末中心区提升；所以同一座位在同一星期下每次刷新都一致，便于演示和测试。

### 汇报时可说

> 我们没有把热度地图做成单纯的颜色装饰，而是把座位级数据用高斯核平滑成连续场。它可以帮助用户先判断区域，再精确选择座位；同时使用确定性数据，避免演示时每次刷新结果不同。

### 建议演示

打开热度图后切换“周一”“周六”“一周综合”，指出周末中心区会更热，但座位仍可单独选择。

## 2. 模块 2：PC 与手机的 Canvas 选座

### 要讲什么

Canvas 很适合一次绘制 100、200、300 个座位，却天然没有 DOM 按钮的交互和语义。更困难的是 PC 与手机对“拖动”的理解完全不同：PC 希望框选，手机通常是在滚动或缩放。

### 实现一：高分屏坐标统一

```js
export function prepareCanvas(canvas, width, height) {
  const ratio = Math.min(2, globalThis.devicePixelRatio || 1);
  canvas.width = Math.round(width * ratio);
  canvas.height = Math.round(height * ratio);
  canvas.style.width = `${width}px`;
  canvas.style.height = `${height}px`;
  const context = canvas.getContext('2d');
  context.setTransform(ratio, 0, 0, ratio, 0, 0);
  return context;
}
```

Canvas 的内部像素尺寸按 `devicePixelRatio` 放大，但 CSS 尺寸保持逻辑尺寸；随后用同样的比例变换绘制。这保证 Retina 屏幕上的座椅边缘清晰，也让命中检测仍使用统一的逻辑坐标。

### 实现二：先识别手势，再执行动作

源码位置：[`src/ui/controllers/SeatMapController.js`](../src/ui/controllers/SeatMapController.js)

```js
const PAN_THRESHOLD = 7;

if (!touchSelect.active && Math.hypot(deltaX, deltaY) >= PAN_THRESHOLD) {
  touchSelect.active = true;
  this._suppressSyntheticClick();
}
```

移动距离小于 7 像素时按“点按”处理；超过阈值后才转为拖动。这样用户在手机上想轻触一个座位时，不会因为手指的微小抖动误触发平移或连续选座。

手机同时支持：

```js
const nextScale = this.pinch.scale *
  (pointerDistance(left, right) / this.pinch.distance);
const next = this._pinchViewAt(midpoint, nextScale);
```

双指距离的比例决定新缩放级别，`_pinchViewAt` 以两指中点为锚点计算新的平移量。因此放大后，用户手指下的座位仍留在手指下，而不是突然跳到别处。

代码还加入三项防误操作设计：

- 在边界外平移时使用 `rubberband` 阻尼，松手后弹回可视范围；
- 触摸选座沿手指路径采样，避免快速划过时漏掉座位；
- 轮椅位和陪同席只允许点按，不允许滑动连选，防止无意占用特殊资源。

### 无障碍补充

Canvas 获得焦点后，方向键按“同行左右、最近上下行”移动虚拟焦点，空格键切换座位；同时页面维护隐藏的语义按钮层，使屏幕阅读器能读出排号、座号、附加费、座位类型和状态。Canvas 因此不是不可访问的黑盒。

### 汇报时可说

> 我们没有把 PC 的拖拽交互直接搬到手机上。控制器先判断用户是轻触、拖动还是双指缩放，再决定是否执行选座；这避免了移动端最常见的“滑动时误选座”。

## 3. 模块 1：约束优先的智能推荐选座

### 要讲什么

“推荐一个好座位”不是只比较离银幕的距离。多人连座、已售库存、儿童和长者的座位建议、无障碍通行、陪同席规则、过道和价格经常互相冲突。项目将它们区分为硬约束与可解释的软偏好。

### 第一步：生成同排和相邻排候选

```js
function contiguousWindows(seats, count) {
  for (let start = 0; start <= seats.length - count; start++) {
    const candidate = seats.slice(start, start + count);
    if (candidate.every((seat, index) =>
      index === 0 || seat.columnIndex === candidate[index - 1].columnIndex + 1
    )) windows.push(candidate);
  }
}
```

这是同排连座的滑动窗口。对于不少于 3 人的朋友、家庭或团体，算法还枚举相邻两排的紧凑方案：两排必须相邻、中心位置允许小范围偏移、分区必须一致，并限制两排人数差。资源不足时，用户不会只得到“没有座位”，而是可能得到前后对齐的紧凑布局。

### 第二步：硬约束过滤

候选座位会重新构造成 `BookingDraft`，再统一经过 `validateSeatSelection` 校验，而不是在推荐函数内复制规则：

```js
const validation = validateSeatSelection({
  draft: selected.value,
  auditorium,
  inventory,
  policy
});
if (!validation.ok) continue;
```

校验器负责以下不可突破的规则：

- 票数必须等于座位数，且不能选择已售或他人锁定的座位；
- 无台阶偏好要求所有座位 `stepFree`；
- 陪同席必须与对应轮椅位同时选择，并要求用户确认用途；
- 跨分区只有在同排真正连续时才允许；
- 不允许本次选择在两个不可用座位之间制造一个“孤座”。

### 第三步：分层排序与降级说明

排序不是加权求和一把梭，而是词典序优先级：

1. 先最少违反儿童避开前三排、长者避开后三排的建议；
2. 用户正在调整推荐时，优先保留已有座位、缩小移动距离；
3. 优先同排、两排更对齐、少跨过道；
4. 再比较顾问偏好匹配、位置偏好、观影体验和附加费。

如果存在年龄合规候选，就完全排除不合规候选；只有不存在任何合规布局时才放宽，并输出 `age-relaxed`、`adjacent-rows`、`cross-aisle` 或 `compromise` 等降级标签。最终最多保留 5 组不同排次的方案，避免给用户 5 个看起来完全一样的答案。

### 汇报时可说

> 推荐算法先保证“不犯错”，再追求“更舒服”。例如无台阶通行是硬约束，儿童和长者的排次是优先满足的建议；如果真的无法同时满足，系统不会悄悄替用户决定，而会说明放宽了哪一条。

### 建议演示

选 3--4 张包含儿童或长者票，先点一键选座，再反复点“换一组”。可展示同排方案和相邻两排方案，以及每个方案的解释文本。

## 4. AI 顾问：自然语言偏好到可审计向量

### 要讲什么

AI 的职责不是直接输出“第几排第几座”，而是把用户的一句话翻译成算法可消费的结构化偏好；库存、无障碍和连座仍由本地规则引擎最终裁决。

### 六维意图模型

[`SeatPreferenceIntent.js`](../src/domain/booking/SeatPreferenceIntent.js) 定义六个范围为 0--100 的维度：

| 维度 | 含义 |
|---|---|
| `screenDistance` | 0 为靠近银幕，100 为靠后 |
| `centerAlignment` | 0 为靠边，100 为居中 |
| `surroundingSpace` | 周边空位程度 |
| `priceLevel` | 座位附加费水平 |
| `lowDisturbance` | 基于布局和占用率估计的少受打扰程度 |
| `egressEase` | 靠近过道、无台阶等进出便利性 |

每个维度同时有目标值与权重。例如“带老人、安静、别太贵”会提高 `egressEase`、`lowDisturbance` 和 `priceLevel` 的相应权重；算法可显示每个候选的真实得分、目标值和权重。

### AI 服务与本地兜底

```js
const intent = await interpretSeatPreferenceWithDeepSeek({ preferenceText, context });
if (intent) {
  sendJson(response, 200, { ok: true, source: 'deepseek', intent });
  return;
}
sendJson(response, 200, {
  ok: true,
  source: 'fallback',
  intent: interpretSeatPreferenceLocally(preferenceText, context)
});
```

服务端限制输入长度、清洗上下文、设置 8 秒超时，并要求模型返回 JSON。模型没有密钥、网络或返回格式时，关键词规则引擎仍可识别“安静”“过道”“轮椅”“预算”等偏好。因此 AI 服务失败不会中断选座流程。

### 为什么 AI 不能绕过规则

```js
const candidates = recommendSeatBlocks({
  draft, auditorium, inventory, advisorIntent
});
```

`advisorIntent` 只参与已经通过库存与无障碍校验的候选的比较。也就是说：AI 不知道也不决定具体座位号；它只能改变“合法候选中哪个更贴近用户偏好”的排序。这使 AI 输出可解释、可回退、可测试。

### 汇报时可说

> 我们把 AI 定位为“偏好翻译器”，而不是“决策替代者”。它把自然语言转成六维目标和权重，本地算法再在合法座位中排序；即使模型服务不可用，规则引擎也能稳定工作。

### 建议演示

输入“带老人，想安静一点，最好别太贵，进出方便”，展示解析后的标签、多个预览方案和“采用方案”前不会写入订单的交互边界。

## 5. 结尾与问答准备

### 一句话总结

SmartCinema 的核心不是“画了一个座位图”，而是让**可视化、跨端交互、约束优化和 AI 偏好理解**在同一套业务规则下协作。

### 可能被问到的问题

**Q：热度数据是真实数据吗？**
A：不是。它是基于座位位置、当前占用和星期因子的确定性演示数据，目的是验证热力场与决策辅助的交互设计，不宣称真实商业客流。

**Q：为什么不用 AI 直接选座？**
A：AI 擅长理解模糊语言，但库存、无障碍和连座规则必须可验证。把 AI 限制在“意图解析”，可避免它编造座位，也能在服务不可用时回退。

**Q：为什么不只用 DOM 按钮画座位？**
A：100--300 个座位叠加热度、缩放和平移时，Canvas 更适合统一渲染与命中检测；同时我们额外维护语义层和键盘导航，补足 Canvas 的无障碍短板。

**Q：推荐会不会为了凑连座牺牲无障碍？**
A：不会。无台阶通行、陪同席配对和库存可用性是硬约束；没有完整合规布局时，系统会建议其他场次，而不是暗中放宽该规则。
